验证实施是否匹配变更工件（规格、任务、设计）。

**输入**：可选择在 `/opsx:verify` 后指定变更名称（例如 `/opsx:verify add-auth`）。如果省略，检查是否可以从对话上下文推断。如果模糊或有歧义，你必须提示可用的变更。

**步骤**

1. **如果没有提供变更名称，提示选择**

   运行 `openspec list --json` 获取可用变更。使用 **AskUserQuestion 工具** 让用户选择。

   显示有实施任务的变更（任务工件存在）。
   如果可用，显示每个变更使用的模式。
   将有未完成任务的变更标记为"（进行中）"。

   **重要**：不要猜测或自动选择变更。始终让用户选择。

2. **检查状态以了解模式**
   ```bash
   openspec status --change "<name>" --json
   ```
   解析 JSON 以了解：
   - `schemaName`：正在使用的工作流（例如 "spec-driven"）
   - 此变更存在哪些工件

3. **获取变更目录并加载工件**

   ```bash
   openspec instructions apply --change "<name>" --json
   ```

   返回变更目录和上下文文件。从 `contextFiles` 读取所有可用的工件。

4. **初始化验证报告结构**

   创建包含三个维度的报告结构：
   - **完整性**：跟踪任务和规格覆盖
   - **正确性**：跟踪需求实施和场景覆盖
   - **一致性**：跟踪设计遵循和模式一致性

   每个维度可以有 CRITICAL（严重）、WARNING（警告）或 SUGGESTION（建议）级别的问题。

5. **验证完整性**

   **任务完成度**：
   - 如果 contextFiles 中存在 tasks.md，读取它
   - 解析复选框：`- [ ]`（未完成）vs `- [x]`（已完成）
   - 统计已完成 vs 总任务数
   - 如果存在未完成任务：
     - 为每个未完成任务添加 CRITICAL 问题
     - 建议："完成任务：<描述>" 或 "如果已实施则标记为完成"

   **规格覆盖**：
   - 如果 `openspec/changes/<name>/specs/` 中存在增量规格：
     - 提取所有需求（标记为 "### Requirement:" 的）
     - 对于每个需求：
       - 在代码库中搜索与需求相关的关键词
       - 评估实施是否可能存在
     - 如果需求似乎未实施：
       - 添加 CRITICAL 问题："未找到需求：<需求名称>"
       - 建议："实施需求 X：<描述>"

6. **验证正确性**

   **需求实施映射**：
   - 对于增量规格中的每个需求：
     - 在代码库中搜索实施证据
     - 如果找到，记录文件路径和行范围
     - 评估实施是否匹配需求意图
     - 如果检测到偏差：
       - 添加 WARNING："实施可能与规格不一致：<详情>"
       - 建议："对照需求 X 审查 <file>:<lines>"

   **场景覆盖**：
   - 对于增量规格中的每个场景（标记为 "#### Scenario:" 的）：
     - 检查代码中是否处理了条件
     - 检查是否存在覆盖该场景的测试
     - 如果场景似乎未被覆盖：
       - 添加 WARNING："场景未被覆盖：<场景名称>"
       - 建议："为场景添加测试或实施：<描述>"

7. **验证一致性**

   **设计遵循度**：
   - 如果 contextFiles 中存在 design.md：
     - 提取关键决策（查找 "Decision:"、"Approach:"、"Architecture:" 等部分）
     - 验证实施是否遵循这些决策
     - 如果检测到矛盾：
       - 添加 WARNING："未遵循设计决策：<决策>"
       - 建议："更新实施或修改 design.md 以匹配实际情况"
   - 如果没有 design.md：跳过设计遵循度检查，注明 "没有 design.md 可供验证"

   **代码模式一致性**：
   - 审查新代码与项目模式的一致性
   - 检查文件命名、目录结构、编码风格
   - 如果发现显著偏差：
     - 添加 SUGGESTION："代码模式偏差：<详情>"
     - 建议："考虑遵循项目模式：<示例>"

8. **生成验证报告**

   **总结评分卡**：
   ```
   ## 验证报告：<change-name>

   ### 总结
   | 维度     | 状态             |
   |---------|-----------------|
   | 完整性  | X/Y 个任务，N 个需求 |
   | 正确性  | M/N 个需求已覆盖   |
   | 一致性  | 已遵循/有问题      |
   ```

   **按优先级列出的问题**：

   1. **CRITICAL**（归档前必须修复）：
      - 未完成的任务
      - 缺失的需求实施
      - 每个都有具体、可操作的建议

   2. **WARNING**（应该修复）：
      - 规格/设计偏差
      - 缺失的场景覆盖
      - 每个都有具体的建议

   3. **SUGGESTION**（可选改进）：
      - 模式不一致
      - 小改进
      - 每个都有具体的建议

   **最终评估**：
   - 如果有 CRITICAL 问题："发现 X 个严重问题。请在归档前修复。"
   - 如果只有警告："没有严重问题。Y 个警告需要考虑。可以归档（带有已注明的改进）。"
   - 如果全部通过："所有检查通过。可以归档。"

**验证启发式方法**

- **完整性**：关注客观的检查清单项（复选框、需求列表）
- **正确性**：使用关键词搜索、文件路径分析、合理推断 - 不要求完美确定性
- **一致性**：寻找明显的矛盾，不要挑剔风格
- **误报处理**：不确定时，优先使用 SUGGESTION 而非 WARNING，WARNING 而非 CRITICAL
- **可操作性**：每个问题必须有具体的建议，适用时包含文件/行引用

**优雅降级**

- 如果只有 tasks.md：只验证任务完成度，跳过规格/设计检查
- 如果 tasks + specs：验证完整性和正确性，跳过设计
- 如果有完整工件：验证所有三个维度
- 始终注明跳过了哪些检查以及原因

**输出格式**

使用清晰的 Markdown 格式：
- 表格用于总结评分卡
- 分组列表用于问题（CRITICAL/WARNING/SUGGESTION）
- 代码引用格式：`file.ts:123`
- 具体、可操作的建议
- 不要模糊的建议如 "考虑审查一下"
